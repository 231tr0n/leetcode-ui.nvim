                                                                      *LeetCode*
*leetcode-ui* LeetCode UI for Neovim

A command-driven LeetCode client. The whole interface lives in one central
window: problem description, solution editor, test console, and information
are tabs in that window. Statistics use the same window.

No keymaps are created by the plugin. Every action is available as a
`:LeetCode` subcommand (also available as `:Leetcode`), so you can map
exactly the actions you use:

>lua
  vim.keymap.set('n', '<leader>lr', '<cmd>LeetCode run<cr>', { desc = 'LeetCode: run' })
  vim.keymap.set('n', '<leader>ls', '<cmd>LeetCode submit<cr>', { desc = 'LeetCode: submit' })
<

Features:

- Browse problems with `mini.pick` or |vim.ui.select()|.
- Read parsed descriptions and hints.
- Edit, run, and submit solutions with draft persistence.
- Run Python 3 solutions locally with the bundled harness.
- Show progress statistics and session information.
- Import session cookies from supported browsers.

Commands:

- `:LeetCode list [difficulty]` - browse problems, optionally filtered.
- `:LeetCode daily` - open the daily challenge.
- `:LeetCode random [difficulty]` - open a random problem.
- `:LeetCode open <slug>` - open a problem by its title slug.
- `:LeetCode description`, `:LeetCode code`, `:LeetCode console`,
  `:LeetCode info` - show a question tab.
- `:LeetCode next`, `:LeetCode prev` - cycle question tabs.
- `:LeetCode run [index]` - run all testcases or one testcase.
- `:LeetCode submit` - submit the current solution.
- `:LeetCode reset` - restore the starter snippet.
- `:LeetCode format` - format the current solution.
- `:LeetCode language [slug]` - switch language (picker without `slug`).
- `:LeetCode case add [input]`, `:LeetCode case edit [index] [input]`,
  `:LeetCode case delete [index]`, `:LeetCode case next`,
  `:LeetCode case prev` - manage testcases. Use `\n` for newlines in
  one-line command input.
- `:LeetCode stats` - show progress statistics.
- `:LeetCode session` - show the current session.
- `:LeetCode refresh [difficulty]` - clear the problem cache and reopen.
- `:LeetCode close` - close the central window.
- `:LeetCode help` - show a command summary in the central window.

------------------------------------------------------------------------------
                                                                *LeetCodeConfig*
*leetcode-ui-config* Configuration for leetcode-ui

Configuration is validated and applied by |leetcode-ui.setup()|.

Nested tables are replaced whole (not deep-merged), like in mini.nvim.
Supply the complete nested table when overriding one.

Options:

- `url` (`string`) - LeetCode domain used for API and web URLs.
- `lang` (`string`) - default solution language slug.
- `languages` (`table|nil`) - allow-list of language slugs for the picker.
- `cookies` (`table`) - `LEETCODE_SESSION` and `csrftoken` values.
- `cookie_file` (`string|nil`) - Netscape cookie jar consumed by curl.
- `storage_path` (`string|nil`) - cache and draft root.
- `browser` (`string`) - cookie import source: `auto`, `firefox`,
  `epiphany`, `safari`, `chrome`, `brave`, `edge`, `chromium`, or `none`.
- `browser_paths` (`table`) - per-browser database path overrides.
- `local_runner` (`boolean`) - prefer bundled local runners for `run`.
- `binaries` (`table`) - executable overrides for local runners.
- `runner_timeout` (`number`) - local runner timeout in seconds.
- `no_local` (`table`) - language slugs that always run online.
- `float_width`, `float_height` (`number`) - central window size.
- `float_border` (`string|nil`) - central window border.
- `picker` (`string`) - `auto`, `mini`, or `builtin`.
- `cooldown` (`number`) - problem-list cache lifetime in minutes.
- `hide_premium` (`boolean`) - hide premium-only problems.
- `notifications` (`boolean`) - show informational notifications.
- `icons` (`table`) - status and testcase icon overrides.

Default configuration:

>lua
  require('leetcode-ui').setup({
    url = 'leetcode.com',
    lang = 'python3',
    languages = nil,
    cookies = { LEETCODE_SESSION = nil, csrftoken = nil },
    cookie_file = nil,
    storage_path = nil,
    browser = 'auto',
    browser_paths = {},
    local_runner = true,
    binaries = {},
    runner_timeout = 30,
    no_local = {},
    float_width = 120,
    float_height = 36,
    float_border = nil,
    picker = 'auto',
    cooldown = 60,
    hide_premium = false,
    notifications = true,
  })
<

                                                                  *LeetCodeAuth*
*leetcode-ui-auth* Session handling based on LeetCode cookies

Cookies are resolved in this order:
1. `cookie_file`: a Netscape-format cookie jar consumed by curl directly.
2. `cookies` from configuration.
3. Environment variables `LEETCODE_SESSION` and `CSRFTOKEN`.
4. LeetCode cookies imported from a supported browser.

|LeetCodeAuth.verify()| lazily runs the `userStatus` GraphQL query and
caches `{ signed_in, name, is_premium }` for the rest of the session.

                                                               *LeetCodeBrowser*
*leetcode-ui-browser* Automatic cookie import from browsers

Supported sources:
- Firefox (`cookies.sqlite`, plain SQLite).
- Chromium-family browsers (`Cookies` SQLite). Legacy `v10` blobs decrypt
  via the Chromium scheme using `openssl`; `v11+` blobs require keyring
  access and report an explicit error when it is unavailable.
- Epiphany and Safari where available.

Browser databases are copied to a temporary directory before reading, so
browser locks are untouched. Only the two LeetCode cookie names on
`%.leetcode.com` hosts are queried; decrypted values never hit the disk.

                                                                   *LeetCodeNet*
*leetcode-ui-net* HTTP layer on top of curl

|LeetCodeNet.request()| works both inside a coroutine (yields until the
request finishes) and on the main thread (uses blocking `vim.system`).

Transient failures (403/429/5xx) are retried with short backoff because
LeetCode's middleware occasionally returns those for valid requests.


------------------------------------------------------------------------------
                                                         *LeetCodeNet.request()*
                         `LeetCodeNet.request`({opts})
Perform an HTTP request.

Options:
- `url` (string, required)
- `method` (`'GET'|'POST'|'PUT'|'DELETE'`, default `'GET'`)
- `headers` (array of raw `'Name: value'` strings)
- `body` (string|nil raw request body)
- `timeout` (number seconds, default 30)
- `retries` (number of transient-failure retries, default 3)

Returns `{status, headers, body}` and an error string on transport failure.
Inside a coroutine, yields until the request completes.

Parameters ~
{opts} `(table)` Request options.
Return ~
`(table|nil)` Response
Return ~
`(string|nil)` Error

------------------------------------------------------------------------------
                                                                *LeetCodeRunner*
*leetcode-ui-runner-common* Local runner plumbing

Machinery shared by language harnesses:
- decode question `metaData` (params, return type, system-design form),
- split testcase `data_input` into raw parameter lines,
- resolve a language harness and its availability,
- spawn the local run and normalize results.

Language harness contract (modules under `runner/langs/<slug>`):
- `available()` returns a boolean and an optional note.
- `run(dir, question, code, meta, params, data_input)` creates workspace
  files under `dir` and returns argv for |vim.system()|.

------------------------------------------------------------------------------
                                                          *LeetCodeRunnerPython*
*leetcode-ui-runner-python3* Python3 local runner

Wraps the user's `class Solution` with LeetCode-standard data structures,
a decoder for raw testcase lines, and a serialized return value.
System-design problems drive the `classname` object through the method list
(see |leetcode-ui-runner-common|).

Run contract: `argv = [python, main.py, lines_json, specs_json, mode]`
- `lines_json` - array of raw testcase lines.
- `specs_json` - normal mode: array of parameter type strings; system-design
  mode: array of `{ name, types = {...} }` per method.
- `mode` - `'normal'` or `'systemdesign'`.
