------------------------------------------------------------------------------
                                                                      *LeetCode*
A command-driven LeetCode client. The whole interface lives in one central
window: problem description, solution editor, test console, and information
are tabs in that window. Statistics use the same window.

# Setup ~

Call |LeetCode.setup()| with your options. All settings are optional; see
|leetcode-ui-config| for every option and the defaults. Every call replaces
the complete configuration: options omitted from the new table return to
their defaults instead of keeping values from an earlier call.

Changing `url`, `storage_path`, or credential-related options closes the
central window (question, statistics, and help views) after drafts are
saved. `storage_path` changes may migrate saved data; `url` and credential
changes also reset cached authentication. If a draft cannot be saved, setup
raises an error.

>lua
  require('leetcode-ui').setup({})
<

No action keymaps are created by the plugin. Every action is available as a
`:LeetCode` subcommand, so you can map exactly the actions you use:

>lua
  vim.keymap.set('n', '<leader>lr', '<cmd>LeetCode question run<cr>',
    { desc = 'LeetCode: run' })
  vim.keymap.set('n', '<leader>ls', '<cmd>LeetCode question submit<cr>',
    { desc = 'LeetCode: submit' })
<

# Features ~

- Browse problems with `mini.pick` or |vim.ui.select()|.
- Read parsed descriptions, with hints hidden by default.
- Edit solutions with draft and testcase persistence.
- Run and submit solutions through LeetCode's API.
- Format with the remote formatter when available, otherwise CLI
  formatters or LSP.
- Show progress statistics and session information.
- Show inline progress while the problem list loads.
- Render Description, Info, Statistics, and Help as Markdown when
  `render-markdown.nvim` is loaded and enabled.
- Import session cookies from supported browsers (disabled by default).

# Commands ~

Browsing and account views:

- `:LeetCode` or `:LeetCode list [difficulty]` - browse problems.
- `:LeetCode daily` - open the daily challenge.
- `:LeetCode random [difficulty]` - open a random problem.
- `:LeetCode open <slug>` - open a problem by its title slug.
- `:LeetCode stats` - show progress statistics.
- `:LeetCode session` - show the current session.
- `:LeetCode refresh [difficulty]` - fetch a fresh problem list and reopen.
- `:LeetCode help` - show a command summary in the central window.

Question-window actions live under `:LeetCode question`:

- `:LeetCode question description`, `:LeetCode question code`,
  `:LeetCode question console`, `:LeetCode question info` - show a tab.
- `:LeetCode question hints [show|hide]` - show, hide, or toggle hints
  when no argument is given (hidden by default).
- `:LeetCode question next`, `:LeetCode question prev` - cycle tabs.
- `:LeetCode question run [index]` - run all testcases or one testcase.
- `:LeetCode question submit` - submit the current solution.
- `:LeetCode question reset` - restore the starter snippet.
- `:LeetCode question format` - format the current solution.
- `:LeetCode question language [slug]` - switch language.
- `:LeetCode question case add <input>`,
  `:LeetCode question case edit <index> <input>`,
  `:LeetCode question case delete <index>`,
  `:LeetCode question case reset`,
  `:LeetCode question case next`, `:LeetCode question case prev`
  - manage testcases. Use `\n` for newlines in one-line command input.
- `:LeetCode question close` - close the question window.

# Requirements ~

- Neovim stable (0.12 or newer; `vim.system`, `vim.uv`, and `vim.lsp`).
- `curl` - required for all LeetCode API and remote formatting requests.
- `python3` - required only for browser cookie import; SQLite-backed
  browsers also need the `sqlite3` module.
- `openssl` - optional; used for supported Chromium-family `v10` and `v11`
  cookie decryption.
- `secret-tool` on Linux or `security` on macOS - optional; used for
  keyring-protected cookies (Linux `v11`, macOS `v10`/`v11`).
- `mini.nvim` - optional; run `require('mini.pick').setup()` for the
  picker backend and `require('mini.clue').setup()` for key hints. Clue
  triggers are enabled inside the central window when it is set up.
- `render-markdown.nvim` - optional; renders Markdown views in the central
  window when it is loaded and enabled.
- `npm`/`npx` - optional; enables `prettier = true` to format JavaScript
  and TypeScript through `npx prettier`.
- A language server such as `lua-language-server`, `clangd`, or `ruff` -
  optional; provides diagnostics and completion, plus LSP formatting when
  the server supports it.
- Optional CLI formatters: `prettier`, `black`, `clang-format`, `gofmt`,
  `rustfmt`, or `google-java-format`.

No LuaRocks or external Lua packages are required.

# Browser cookie caution ~

Browser cookie import is disabled by default (`browser = 'none'`). When
enabled, the plugin reads LeetCode cookies directly from your browser's
on-disk cookie database and may decrypt Chromium-family values using system
keyring tools and `openssl`. These cookies grant access to your LeetCode
account; only enable this if you understand the risk. Prefer `cookie_file`
or environment variables when possible. Linux is the tested Chromium
decryption path; macOS uses the Keychain and PBKDF2 and is covered by mocked
unit tests, not a native macOS CI runner. Encrypted Chromium cookies on
Windows are not supported.

------------------------------------------------------------------------------
                                                                *LeetCodeConfig*
*leetcode-ui-config* Configuration for leetcode-ui

Configuration is validated and applied by |LeetCode.setup()|.

Each call to |LeetCode.setup()| replaces the whole configuration. Unspecified
options return to their defaults; values from a previous call are not
merged. Nested tables are replaced whole, except `icons`, which is merged
with the defaults so partial icon overrides are supported.

Options:

- `url` (`string`) - LeetCode domain used for API, formatter, and web URLs.
- `lang` (`string`) - default solution language slug.
- `languages` (`table|nil`) - allow-list for solution languages and the
  language picker.
- `cookies` (`table`) - `LEETCODE_SESSION` and `csrftoken` values.
- `cookie_file` (`string|nil`) - Netscape cookie jar consumed by curl.
- `storage_path` (`string|nil`) - cache, draft, and testcase root.
- `browser` (`string`) - cookie import source: `none` (default), `auto`,
  `firefox`, `epiphany`, `safari`, `chrome`, `brave`, `edge`, or `chromium`.
- `browser_paths` (`table`) - per-browser database path overrides.
- `float_width`, `float_height` (`number`) - preferred central window
  content size, clamped to the usable editor area. Borders are extra.
- `float_border` (`string|nil`) - central window border.
- `picker` (`string`) - `auto` (use `mini.pick` when `MiniPick` is set up),
  `mini` (prefer it explicitly), or `builtin` (use |vim.ui.select()|).
- `cooldown` (`number`) - problem-list cache lifetime in minutes.
- `hide_premium` (`boolean`) - hide premium-only problems from pickers,
  random selection, and completions.
- `show_hints` (`boolean`) - show hints in the Description tab by default.
- `notifications` (`boolean`) - show notifications.
- `markdown` (`boolean`) - render the Description, Info, Statistics, and
  Help views as Markdown when `render-markdown.nvim` is loaded and enabled.
  The Code editor and Console remain unchanged.
- `prettier` (`boolean`) - use `npx prettier` for JavaScript and TypeScript
  solution formatting when `npx` is on `PATH` and `prettier` is not on
  `PATH`. This may download Prettier if it is not installed locally.
- `icons` (`table`) - status and testcase icon overrides. Partial groups are
  merged with the defaults.

Supported language slugs: `bash`, `c`, `cpp`, `csharp`, `dart`, `elixir`,
`erlang`, `golang`, `java`, `javascript`, `kotlin`, `php`, `python`,
`python3`, `racket`, `ruby`, `rust`, `scala`, `swift`, and `typescript`.
The `python` slug is normalized to `python3`.

Default configuration:

>lua
  require('leetcode-ui').setup({
    url = 'leetcode.com',
    lang = 'python3',
    languages = nil,
    cookies = { LEETCODE_SESSION = nil, csrftoken = nil },
    cookie_file = nil,
    storage_path = nil,
    browser = 'none',
    browser_paths = {},
    float_width = 120,
    float_height = 40,
    float_border = nil,
    picker = 'auto',
    cooldown = 60,
    hide_premium = false,
    show_hints = false,
    notifications = true,
    markdown = true,
    prettier = false,
    icons = {
      status = { solved = '✔', attempted = '✘', todo = '○', active = '◈' },
      case = { passed = '✔', failed = '✘', unknown = '○', err = '✗' },
    },
  })
<

Highlight groups:

All groups except `LeetCodeCursor` are linked to existing highlight groups
by default, so colorschemes control them. Override any group after setup
with |nvim_set_hl()|:

>lua
  require('leetcode-ui').setup({})
  vim.api.nvim_set_hl(0, 'LeetCodeOk', { fg = '#00ff00' })
<

- `LeetCodeOk` -> `DiagnosticOk`
- `LeetCodeErr` -> `DiagnosticError`
- `LeetCodeWarn` -> `DiagnosticWarn`
- `LeetCodeDim` -> `Comment`
- `LeetCodeTitle` -> `Title`
- `LeetCodeCode` -> `Identifier`
- `LeetCodeLink` -> `DiagnosticInfo`
- `LeetCodeItalic` -> `@markup.italic`
- `LeetCodeEasy` -> `String`
- `LeetCodeMedium` -> `DiagnosticWarn`
- `LeetCodeHard` -> `DiagnosticError`
- `LeetCodeHeader` -> `@markup.heading`
- `LeetCodeQuestionTitle` -> `LeetCodeWinBar`
- `LeetCodeTab` -> `TabLine` (inactive winbar tabs)
- `LeetCodeTabActive` -> `PmenuSel` (active winbar tab)
- `LeetCodeCursorLine` -> `CursorLine`
- `LeetCodeCursor` - hidden cursor used in read-only tabs
- `LeetCodeCodeNormal` -> `Normal` (Code tab background)
- `LeetCodeNormalFloat` -> `NormalFloat`
- `LeetCodeFloatBorder` -> `FloatBorder`
- `LeetCodeWinBar` -> `WinBar`
- `LeetCodeWinBarNC` -> `WinBarNC`

Read-only tabs hide the cursor, use `LeetCodeCursorLine` for the active
line, and keep the `LeetCodeNormalFloat` background. The Code tab uses the
normal `Cursor` and `CursorLine` groups and the `LeetCodeCodeNormal`
background.

                                                                  *LeetCodeAuth*
*leetcode-ui-auth* Session handling based on LeetCode cookies

Requests use `cookie_file` when configured: curl consumes the Netscape jar
directly. Otherwise cookies are resolved from configuration, environment
variables (`LEETCODE_SESSION` and `CSRFTOKEN`), then supported browsers
when `browser` import is enabled.

|LeetCodeAuth.verify()| lazily runs the `userStatus` GraphQL query and

                                                               *LeetCodeBrowser*
*leetcode-ui-browser* Automatic cookie import from browsers

Supported sources:
- Firefox (`cookies.sqlite`, plain SQLite).
- Chromium-family browsers (`Cookies` SQLite). Linux uses the tested
  Chromium key derivation; macOS uses the Keychain password and PBKDF2.
  Keyring-protected `v11` blobs (and macOS `v10`) report an explicit error
  when the keyring is unavailable. Encrypted Chromium cookies on Windows are
  not supported.
- Epiphany and Safari where available.

SQLite browser databases and available WAL sidecars are copied to a
temporary directory before reading, so browser locks are untouched. Only
the two LeetCode cookie names on the configured domain and its subdomains
are queried. Browser readers do not persist decrypted values; network
requests may place session headers in a private temporary directory.
Chromium decryption passes the derived key to the `openssl` CLI as an
argument, which can be visible to other local users on shared systems.
With `browser = 'auto'`, sources are checked in priority order and the first
complete pair is used. If no source has a complete pair, the source with
the most LeetCode cookies is used.

                                                               *LeetCodeStorage*
*leetcode-ui-storage* Local caching and solution drafts

Layout (default `stdpath('data')/leetcode-ui`, override with
`storage_path` in |LeetCode.setup()|):

- `cache.json` - problem list, credential identity, domain, list/status
  revisions, and timestamps.
- `drafts/{domain}/{slug}.{langSlug}` - raw typed code per question and
  language.
- `testcases/{domain}/{slug}.json` - custom testcase inputs per question.

`testcases/{slug}.json` are migrated into the `leetcode.com` layout on
first read; they are left untouched when another domain is configured.
Changing `storage_path` copies saved drafts and testcases into the new root.
A target nested inside the current root is rejected. The first setup in a
new process does not migrate from the default root.

------------------------------------------------------------------------------
                                                             *LeetCodeRunnerApi*
*leetcode-ui-api-runner* Test-run and submit flows

Flow: POST code to LeetCode, then poll `/submissions/detail/{id}/v2/check/`
until a final status arrives. Terminal judging states (`FAILURE`,
`REVOKED`) and `ai_state = FAILURE` are returned as errors; `SUCCESS`
without a status code is also an error. Normalize the result for
|leetcode-ui-console|.

Normalized result:
`{ status, ok, message, runtime_ms, memory_bytes, correct, total, compare,
stdouts, pretty_stdout, answers, expected_answers, input, expected_output,
code_output, lang, is_submit, raw }`.
